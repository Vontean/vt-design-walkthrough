# 取证、问题颗粒度与集中复核

## 当场形成一条记录

1. 保存原始状态和触发步骤；必要时重复一次确认复现条件。跨版本、偶发或时间性问题写出观察次数和证据限制。
2. 到精确 Figma 节点核对布局/状态/规则，将 actual 与 expected 分开。实现偏差、新设计要求、规则不明确、数据未覆盖分别使用数据契约的 kind。
3. 按独立修改点拆分：例如字号和跳转失败应分别记录；同一个布局问题在两个状态的必要证据可以归同一条。多个平台分别记录用例与问题，通过 related_ids 关联同类问题。
4. title 简要描述具体差异；feedback 写入口/条件、当前表现、实际影响、应如何修改。只提出已有依据或用户确认的精确值；缺规格的优化建议标为待确认。
5. 把完整实际页面截图与完整对应 Figma 画板或规则区域配对，写 annotations.json，执行 render-evidence.py。默认红框实际区域、蓝框设计区域。主图保留原图范围，让研发能识别页面和问题位置；需要看细节时通过 crop 生成补充放大图。用户仅提供局部图时，优先查找同一状态的完整证据；无法取得则注明原图范围限制，保留真实局部证据。静态图只能定位入口的动效问题，附录屏/序列/时刻说明，截图不冒充时间证据。
6. 打开生成图核验：主图显示完整原图、页面可识别、框准确包含目标、两边确为同一功能/状态；小细节可在原附件或补充图中放大查看。原图保持不变，在线展示宽度单独控制。
7. 从 render-manifest.json 按 ID 写回生成图路径和原图路径，更新 findings.json 和相关用例；立即追加日志，随后继续走查。

完成：研发可凭该条独立找到触发位置、理解一件问题、定位正确依据。

## 排序与复核

所有 Page 完成后生成 RECORD.md。按设计功能顺序分组，相近子功能相邻，同组按操作路径排序；一个修正点一行。区分问题与覆盖请求的数量，用户评价有独立列。

交付完整稿供集中复核；不设中途代表性问题审批。用户随时追加的截图先保存并核对，最终一并交付。对确认/撤回/修改决定维护 review、review_note 和 publish，编号保持稳定。设计依据不足的项写出具体待确认问题。

用户确认后校验所选条目，并准备在线交付；未经确认的项留在本地待审。
